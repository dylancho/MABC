## 1. 배경과 문제

공무원은 정해진 공문서 양식(hwpx)에 자료를 옮겨 적는 일에 상당한 시간을 쓴다. 자료는 흩어져 있고, 양식은 기관·연도·사업마다 다르며, 1페이지 기안문부터 수십 페이지 사업계획서까지 형태가 넓다.

기존 LLM으로 이 일을 시키면 두 가지가 실패한다.

1. **서식이 깨진다.** 문서를 재생성하는 방식은 글꼴·표·여백·번호매기기를 보존하지 못한다. 서식이 깨진 문서는 결재를 올릴 수 없으므로 가치가 0이다.
2. **없는 내용을 지어낸다.** 공문서 허위기재는 단순 품질 문제가 아니다.

### 제품 논지

이 제품은 **글을 잘 쓰는 도구가 아니라, 양식을 이해하고 원본을 깨뜨리지 않는 엔진**이다. 대체 불가능한 해자는 다음 두 축에 있다.

- **축 1 — 양식 자동 해부**: 처음 보는 양식을 받아도 "빈 칸이 몇 개이고 각각 무엇을 요구하는가"를 사람 개입 없이 알아낸다.
- **축 4 — hwpx 무손상**: 결과를 한글로 열었을 때 서식·표·여백이 원본 그대로이고 바로 결재를 올릴 수 있다.

문안 작성 품질(문체·분량)은 부차적 목표이며, 타임리AI의 Solar가 담당한다.

### 타깃 사용자

지자체·공공기관 공무원. 예시 페르소나: ○○구청 김주무관 — 매년 12월 관내 비영리법인 40곳의 현황 보고를 정해진 서식으로 취합한다.

## 2. 목표와 비목표

### 목표

- 처음 보는 표 기반 공문서 양식(A)을 해부하여 슬롯 목록을 산출한다.
- 사용자가 가진 자료(B)의 내용을 슬롯에 채워 hwpx로 반환한다.
- 결과 파일이 원본 대비 무손상임을 **바이트 단위로 증명**한다.
- 타임리AI 에이전트에서 대화로 사용 가능하다.

### 입력 B의 범위 (MVP)

B(사용자가 가진 자료)의 형태는 아직 확정되지 않았다. MVP는 **hwpx 문서와 평문
텍스트(대화창 붙여넣기 포함)** 두 가지만 지원한다. B는 슬롯 구조를 갖지 않으므로
`hwpx-core`의 해부 파이프라인을 타지 않고, 본문 텍스트만 추출해
`inspect_source`가 검색 가능한 형태로 보관한다.

엑셀·워드·PDF·이미지는 v2로 미룬다. 다만 **B 추출기를 교체 가능한 어댑터로 분리**
하여, 형식이 늘어나도 `dissect`/`fill`/`verify`에 영향이 없도록 설계한다.

### 비목표 (MVP에서 명시적으로 자름)

- 반복 행 자동 확장 (행 추가는 XML 구조 변경이므로 무손상 원칙과 충돌 → v2)
- 문단형·개요번호형 양식 (검출만 하고 `unsupported`로 표시)
- `.hwp` 구버전 바이너리 포맷 (감지 후 변환 안내만)
- 양식 캐시/학습 (여유 시 추가)
- 계정, 문서 저장소, 협업, 다국어, 결재선 연동

## 3. 실측 근거

설계는 실제 공문서 양식 두 종을 해체하여 검증한 사실 위에 세웠다.

### 3.1 hwpx 컨테이너

ZIP 아카이브. `(서식1) 비영리법인 현황 제출 양식.hwpx` 기준 11개 엔트리.

```
mimetype                 19 B    ← 반드시 첫 엔트리 · 무압축(STORE)
version.xml             310 B
Contents/header.xml   64,053 B   ← 스타일 정의 전부 (글꼴·문단·테두리·번호매기기)
Contents/section0.xml 112,497 B  ← 본문
Contents/content.hpf   1,858 B   ← 매니페스트 (section 파일 목록)
settings.xml            958 B
META-INF/{container.xml, container.rdf, manifest.xml}
Preview/{PrvText.txt, PrvImage.png}
```

### 3.2 셀의 실제 구조

```xml
<hp:tc borderFillIDRef="8">                          <!-- 라벨 셀 -->
  <hp:p paraPrIDRef="4" styleIDRef="0">
    <hp:run charPrIDRef="0"><hp:t>법인명</hp:t></hp:run>
  <hp:cellAddr colAddr="0" rowAddr="2"/>             <!-- 명시적 좌표 -->
  <hp:cellSpan colSpan="1" rowSpan="1"/>             <!-- 병합 정보 -->
  <hp:cellSz width="11176" height="3642"/>

<hp:tc borderFillIDRef="3">                          <!-- 입력 셀 -->
    <hp:run charPrIDRef="0"/>                        <!-- 빈 run: 텍스트 노드 없음 -->
```

확인된 사실:

- 셀마다 좌표(`cellAddr`)와 병합 정보(`cellSpan`)가 명시되어 있다.
- 스타일은 전부 ID 참조(`paraPrIDRef` / `charPrIDRef` / `borderFillIDRef`)이며 실제 정의는 `header.xml`에 있다. 따라서 **본문의 텍스트 노드만 건드리면 서식은 구조적으로 변할 수 없다.**
- 빈 입력 셀은 `<hp:run charPrIDRef="N"/>` 형태로 텍스트 노드 자체가 없다.

### 3.3 두 양식의 통계 — 가설 하나가 반증됨

| 항목 | 서식1 (1p급) | 서식2 (수십p급) |
|---|---|---|
| 파일 크기 (section0.xml) | 111,593 B | 1,857,810 B |
| 셀(`hp:tc`) 수 | 126 | 2,226 |
| `borderFillIDRef` 종류 | 22종 | **98종** |
| 빈 run : 텍스트 run | 52 : 92 | **1,948 : 497** |
| 병합 셀 비율 | **53%** (67/126) | 17% (371/2,226) |
| 체크박스 표기 | `【 】` 18개 | `□` 22개 |
| `paraPrIDRef` 종류 | 6 | 62 |

도출된 설계 결론:

1. **`borderFillIDRef`는 라벨/입력 판별의 주 신호가 될 수 없다.** 98종이면 양식마다 새로 학습해야 하므로 범용성이 없다. 보조 신호로 강등한다.
2. **빈 칸 "찾기"는 쉬운 문제다.** 빈 run이 1,948개 널려 있다. 어려운 문제는 **라벨 귀속** — 이 빈 칸이 무엇을 요구하는가. 개발 자원을 여기에 집중한다.
3. **병합 셀 처리는 전제 조건이다.** 한 양식은 절반 이상이 병합이므로, `cellAddr`을 그대로 읽으면 라벨-값 관계가 깨진다. 그리드 복원이 필수다.

### 3.4 「작성요령」 블록 — 양식이 스스로 채우는 법을 설명한다

서식2 본문에 다음이 포함되어 있었다.

```
사업계획 총괄표 작성요령
□ 일반현황
  ○ 임원정수 : 정관상 임원의 정수 기재
  ○ 임원현원 : 현재 임기중에 있는 임원수 기재
□ 예산현황
  ② 목적사업 수입금 : 목적사업에서 발생한 수입금 전액 기재
```

공문서 양식에는 「작성요령」·「기재요령」·「유의사항」이 거의 항상 붙는다. 이를 파싱해 슬롯의 `hint`로 붙이면, **양식 발급기관이 직접 쓴 지시문**이 매핑 근거가 된다. 추측이 아니라 문서에 있는 사실이므로 정확도와 설명가능성이 동시에 오른다.

### 3.5 슬롯 유형 목록 (서식1 한 장에서 관찰된 것)

| 실제 표기 | 유형 |
|---|---|
| `<법인명><>` | 빈 셀 텍스트 |
| `사단【   】 재단【   】` | 체크박스 (택1) |
| `(우        )`, `(이름)  (전화번호)` | 한 셀 안 인라인 다중 필드 |
| `이사    명(상근   명)` | 공백 슬롯 + 단위 |
| `(예) 청년취업아카데미 300,000,000원 고용노동부` | 예시 행 (지우고 채움) |
| `* 종업원 수가 아닌 법인 구성원을 말함` | 안내문 (건드리면 안 됨) |
| 정관변경 이력 3줄 | 반복 행 (MVP는 기존 행 채움만) |
| `<주사무소 소재지><(우 )>` / `<><><팩스번호>` | 세로 병합 |

## 4. 아키텍처

### 4.1 배포 형태

본선 제출물은 **웹 서비스**이며, LLM은 대회에서 제공되는 **Solar Pro**를 쓴다.
(2026-09-09 확정. 이전 초안의 타임리AI MCP 커넥터 구성은 폐기했다.)

```
  공무원 (브라우저)
    │  A(양식) + B(자료) 업로드
    ▼
┌──────────────────────────────────────────────┐
│  Next.js 웹앱                                 │
│                                              │
│  POST /api/analyze                           │
│    ① dissect(A)  ── hwpx-core, LLM 0회       │
│    ② extract(B)  ── 본문 텍스트 추출          │
│    ③ map()       ── Solar Pro, 여기에만 LLM   │
│    → 슬롯 + 제안값 + 근거 + 되물을 질문        │
│                                              │
│  [사용자가 화면에서 검토·수정]                 │
│                                              │
│  POST /api/fill                              │
│    ④ fill()      ── hwpx-core, LLM 0회       │
│    → 완성 hwpx + 무손상 리포트                │
└──────────────────────────────────────────────┘
```

**서버에 파일을 저장하지 않는다.** 해부가 결정론적이라 같은 A를 다시 올리면 슬롯 id가
그대로 재현되므로, 생성 단계에서 A를 한 번 더 받으면 된다. 세션 저장소도, job 큐도,
blob 스토리지도 필요 없다. 배포와 데모가 그만큼 단순해진다.

**LLM은 `/api/analyze`의 ③단계에만 있다.** 나머지는 전부 순수 함수다.

### 4.1.1 유통 논거 (발표용)

타임리AI는 서울시 '서울AI챗'을 비롯해 전국 지자체·공공기관에 이미 도입되어 있다.
이 웹 서비스의 엔진(`hwpx-core`)은 AI와 네트워크를 모르는 순수 라이브러리이므로,
향후 그런 플랫폼에 얹거나 망분리 온프레미스로 옮길 때 그대로 재사용된다.
타깃(공무원)과 기존 유통 경로가 겹친다는 점은 그대로 유효하다.

### 4.2 핵심 설계 결정 — 바이트 스플라이스

XML을 파싱 후 재직렬화하면 파서가 속성 순서, self-closing 형태(`<hp:run/>` vs `<hp:run></hp:run>`), 공백, 엔티티 표기를 원본과 다르게 출력한다. 내용이 같아도 바이트가 달라지면 **무엇을 건드리지 않았는지 증명할 수 없다.**

따라서:

```
읽기: 파싱한다 (모든 노드에 [start, end] 바이트 오프셋 기록)
쓰기: 파싱 결과를 버리고, 원본 문자열의 [start, end] 구간만 교체한다
```

`법인명` 옆 빈 셀에 값을 넣는 작업은 `<hp:run charPrIDRef="0"/>` → `<hp:run charPrIDRef="0"><hp:t>○○재단</hp:t></hp:run>` 로 해당 구간만 바꾸는 것이며, section0.xml의 나머지 111,000여 바이트는 비트 단위로 동일하다.

이 결정의 효과:

- 무손상이 "주의해서 처리함"이 아니라 **바이트 diff로 증명되는 사실**이 된다.
- 우리가 아직 모르는 hwpx 요소(차트·수식·도형·개체)가 문서에 있어도 자동으로 안전하다. 건드리지 않기 때문이다.
- 수십 페이지 문서에서도 성능이 안정적이다.

대가: 오프셋을 제공하는 SAX 계열 파서가 필요하고, 다중 치환 시 오프셋 재계산을 **내림차순(뒤에서부터)** 으로 처리해야 한다.

### 4.3 ZIP 재포장 제약

hwpx는 OCF 규약을 따르므로 **`mimetype` 엔트리가 반드시 첫 번째이며 무압축(STORE)** 이어야 한다. 일반 ZIP 라이브러리로 재압축하면 한글이 파일을 열지 못한다. 컨테이너 계층에서 이를 강제하고 테스트로 고정한다.

### 4.4 컴포넌트 경계

```
┌─ hwpx-core ──────────────── AI 의존성 0 · 네트워크 의존성 0 · 순수 함수 ─┐
│  container   ZIP 해체/재포장 (mimetype 규약 보존)                        │
│  scan        section XML → 오프셋 달린 노드 인덱스                       │
│  dissect     노드 인덱스 → 슬롯 IR                          [축 1]       │
│  inject      슬롯 IR + 값 → 원본 바이트 스플라이스           [축 4]       │
│  verify      원본 vs 결과 → 무손상 리포트                    [축 4]       │
└─────────────────────────────────────────────────────────────────────────┘
┌─ mcp ───────────────────────────────────────────────────────────────────┐
│  4개 툴 + job 상태 관리 + 파일 저장소                                    │
└─────────────────────────────────────────────────────────────────────────┘
┌─ web ───────────────────────────────────────────────────────────────────┐
│  업로드 / 다운로드 페이지 (최소 UI, 현장 데모 화면 겸용)                  │
└─────────────────────────────────────────────────────────────────────────┘
```

`hwpx-core`는 LLM과 네트워크를 모르므로 실제 양식 파일만으로 오프라인 테스트가 가능하다. 향후 망분리 온프레미스 환경으로 이전할 때 이 계층은 그대로 재사용된다.

### 4.5 기술 스택

- Next.js (App Router) + TypeScript, Vercel 배포
- MCP: Streamable HTTP 원격 서버
- ZIP: `fflate` (엔트리 순서·압축 방식 제어 가능)
- XML: 바이트 오프셋을 제공하는 SAX 파서 (`saxes` 후보 — D1에 검증)
- 파일/상태 저장: Vercel Blob

Python을 혼용하지 않는다. hwpx는 ZIP+XML이므로 Python만의 이점이 없다 (`pyhwpx`는 윈도우 한글 COM 자동화라 서버에서 사용 불가, `hwp5`는 구버전 `.hwp`용). 단일 TypeScript 스택이면 동일한 `hwpx-core` 코드가 서버와 브라우저 양쪽에서 동작하므로, 향후 "파일이 서버로 나가지 않는 모드"를 추가 비용 없이 얻는다.

**우리 서버에는 LLM 호출이 없다.** 모든 언어 판단은 타임리의 Solar가 수행한다.

## 5. HTTP 인터페이스

### 5.1 `POST /api/analyze`

| 입력 (multipart) | |
|---|---|
| `form` | A — 채울 hwpx 양식 (필수) |
| `source` | B — hwpx / txt / md / csv 파일 (선택) |
| `sourceText` | B — 직접 붙여넣은 텍스트 (선택) |

출력: `{ slots, unsupported, formNotes, stats, dissectMs, mapMs, fills, questions, skipped, model }`

- `fills`: `{ id, value, evidence, note }` — `evidence`는 B 원문 인용. 인용을 못 댄 값은 서버에서 버린다.
- `questions`: `{ id, question, candidates }` — 후보가 둘 이상일 때 고르지 않고 올린다.
- B를 주지 않으면 LLM을 호출하지 않고 해부 결과만 돌려준다 (양식 분석 단독 사용).

### 5.2 `POST /api/fill`

| 입력 (multipart) | |
|---|---|
| `form` | A — analyze 때와 같은 파일 |
| `values` | `{ slot_id: value }` JSON |

출력: 완성된 hwpx 바이너리. 무손상 리포트는 `X-Fill-Report` 헤더에 URL 인코딩된 JSON으로 실린다.
검증 실패 시 파일을 만들지 않고 **422**와 실패 사유를 돌려준다.

### 5.3 설계 원칙 — 판단은 LLM이, 엔진은 사실만

`dissect`는 "이 칸에는 사업명이 들어갈 것 같다"고 **추측하지 않는다.** "라벨은 `사업명`,
유형은 text, 좌표는 (2,1), 수용량은 42자, 힌트는 없음"이라는 **관측된 사실만** 반환한다.
매핑 판단은 전적으로 Solar Pro의 몫이다.

이 원칙의 효과: 엔진을 LLM 없이 결정론적으로 테스트할 수 있고(`scripts/check.ts`),
동일 입력에 항상 동일 출력이 나오며, 발표에서 "엔진은 결정론적이고 판단만 AI가 합니다"라고
말할 수 있다.

### 5.4 슬롯 폭증 대응 (실측에서 드러난 문제)

서식2는 슬롯이 **1,941개**로 나온다. 한 프롬프트에 못 넣는다. `mapContentToSlots`가
표 단위로 묶어 40개씩 청크로 쪼개고 4개씩 병렬 호출하며, 상한(`maxSlots`, 기본 400)을
넘는 슬롯은 **비워둔 채로** 남기고 사용자에게 그 사실을 알린다. 조용히 버리지 않는다.

## 6. 슬롯 IR

### 6.1 스키마

```ts
type Slot = {
  id: string                          // "s0.t3.r2c1" — 안정적 주소
  kind: "text" | "choice" | "inline"
      | "example_row" | "repeat_row" | "readonly_note"
  label: string                       // "법인명"
  labelPath: string[]                 // ["기본 사항", "법인명"] — 상위 헤더 체인
  confidence: "high" | "medium" | "low"

  choices?: string[]                  // kind="choice"일 때: ["사단", "재단"]
  hint?: string                       // 「작성요령」에서 추출한 지시문
  unit?: string                       // "천원", "명"
  capacity: { chars: number; lines: number }
}
```

**바이트 오프셋(`anchor`)은 IR에 포함하지 않는다.** job 상태에만 저장하고 에이전트에는 `id`만 노출한다. 2,226셀 양식도 IR이 수 KB로 유지되며, 에이전트가 오프셋을 조작할 경로가 원천적으로 없다.

### 6.2 `capacity` 추정

`cellSz`(width/height)와 해당 셀의 `charPr` 글꼴 크기로 "이 칸에 들어가는 대략적 글자 수와 줄 수"를 계산한다. 명시적 글자수 제한이 없는 양식에서도 에이전트가 분량을 맞출 수 있게 하며, **칸 넘침으로 표 레이아웃이 밀리는 것**을 예방한다. 이것이 공문서 자동화에서 가장 흔한 실패 유형이다.

추정은 근사치이므로 `fill` 단계에서 초과를 차단하지 않고 경고만 한다(§8 항목 3).

## 7. 처리 파이프라인

### 7.1 해부 (`dissect`) — 규칙 기반, LLM 0회

```
section*.xml  (content.hpf 매니페스트로 전체 순회)
   │
 ① 스캔        SAX로 훑으며 모든 노드에 [start, end] 바이트 오프셋 기록
   │
 ② 그리드 복원  colSpan / rowSpan을 펼쳐 논리 격자 생성      ← 병합 53% 대응
   │
 ③ 빈칸 검출    빈 run · 【 】/□ · 공백 4칸 이상 · "(예)" 행 · 밑줄
   │
 ④ 라벨 귀속    같은 행 왼쪽 셀 → 열 헤더 행 → 상위 병합 셀 → 표 제목 순으로
   │            탐색. 실패 시 confidence: "low"로 표시하고 그대로 넘김
   │
 ⑤ 제약 수집    「작성요령」/「기재요령」/「유의사항」 블록 · "(단위: 천원)"
   │            · "N자 이내" · 셀 크기 → capacity
   ▼
 슬롯 IR
```

전 과정이 규칙 기반이므로 오프라인 테스트가 가능하고, 결정론적이며, LLM 비용과 지연이 없다.

### 7.2 주입 (`fill`)

1. 대상 슬롯을 **바이트 오프셋 내림차순으로 정렬** (뒤에서부터 치환해야 앞쪽 오프셋이 밀리지 않음)
2. 케이스별 치환:
   - 빈 run: `<hp:run charPrIDRef="N"/>` → `<hp:run charPrIDRef="N"><hp:t>값</hp:t></hp:run>`
   - 기존 텍스트 보유 run: `<hp:t>…</hp:t>` **내부만** 교체
   - 체크박스: `【   】` → `【 V 】` — **글자 수를 유지**하여 레이아웃 유지
3. XML 이스케이프(`& < >`), 문단 내 줄바꿈은 `<hp:lineBreak/>` (문단 분리가 필요한 다문단 값은 MVP 범위 밖)
4. `fflate`로 재포장 — `mimetype` 첫 엔트리·무압축 유지

### 7.3 검증 (`verify`)

원본과 결과를 비교하여 다음을 리포트한다.

```
무손상 검증 통과                        ← D1 스파이크 실측값 (서식1, 슬롯 6개)
  변경 슬롯       6개
  section0.xml    112,497 B → 112,703 B  (순증 206 B)
  실제 교체       128 B → 334 B  (원본의 0.30%)
  범위 이탈       0건 — 모든 변경이 등록된 슬롯 내부
  header.xml      완전 동일 — 서식·글꼴·표 정의 변경 0건
  그 외 엔트리    전부 무변경
  ZIP             mimetype 선두 유지, 엔트리 순서·압축 방식 동일
```

**변경량 측정 방법 주의.** "첫 변경 위치 ~ 마지막 변경 위치"의 범위로 재면 안 된다.
편집이 문서 곳곳에 흩어져 있으면 그 사이의 무변경 구간까지 삼켜, 실제 0.30%인 것이
22%로 부풀려진다(D1 스파이크에서 실제로 발생). **edit별 교체 바이트를 합산**한다.

**범위 이탈 검사 방법.** 결과물에서 등록된 edit 구간만 원본 값으로 되돌렸을 때
원본과 완전히 일치하면, 모든 변경이 슬롯 내부에서만 일어났음이 증명된다.

`fill`이 이 리포트를 반환하고 에이전트가 사용자에게 전달한다. 검증 실패 시 §8 항목 5에 따라 롤백한다.

## 8. 실패 처리

### 관통 원칙

> **조용히 틀리느니 시끄럽게 묻는다. 확신이 없으면 파일을 내보내지 않는다.**

공문서는 틀리면 결재가 반려되고 지어내면 허위기재다. 또한 사용자는 채워진 칸은 검토하지 않고 빈 칸만 본다. 따라서 **잘못 채우는 것이 채우지 않는 것보다 나쁘다.** 이는 일반적인 AI 제품의 기본값("일단 채워주고 사용자가 고치게")과 반대이며, 의도된 선택이다.

| # | 실패 | 처리 |
|---|---|---|
| 1 | `.hwp` 구버전 바이너리 업로드 | ZIP 매직바이트 검사로 즉시 감지. "한글에서 다른 이름으로 저장 → hwpx로 저장해 주세요" 안내. 가장 빈번히 발생할 실패이므로 안내 문구를 다듬는다 |
| 2 | 라벨 귀속 실패 | 숨기지 않고 `confidence: "low"`로 IR에 노출. 에이전트가 주변 텍스트를 근거로 사용자에게 되묻는다 |
| 3 | 값이 `capacity` 초과 | 주입은 수행하되 `overflow` 목록에 담아 반환. 임의로 자르지 않고 에이전트가 판단 |
| 4 | B에 근거가 없는 슬롯 | **비워둔다.** `unfilled` 목록으로 반환하여 에이전트가 명시적으로 보고. 추측 주입 금지 |
| 5 | `verify` 실패 (변경이 슬롯 범위 밖에서 발생) | **전체 롤백.** 원본과 실패 사유를 반환. 깨진 파일은 내보내지 않는다 |
| 6 | 표 밖 슬롯 / 문단형 양식 | 검출하되 `unsupported`로 표시하고 해당 영역은 건드리지 않는다 |
| 7 | section 파일이 여러 개 | `content.hpf` 매니페스트를 읽어 전부 순회 |
| 8 | 대용량 파싱 지연 | 서식2 기준 1.86MB / 2,226셀. D6에 MCP 툴 응답 시간을 실측하고, 한계를 넘으면 `dissect`를 비동기 job으로 분리 |

4번과 5번은 발표에서 그대로 신뢰 논거가 된다.

### 8.1 LLM 출력을 믿지 않는 두 가드 (실측으로 도입)

프롬프트에 "지어내지 마세요"는 처음부터 있었다. **지켜지지 않았다.**
solar-pro2가 실제로 낸 출력:

```
공익법인 여부      → "비해당"   근거: "…명시된 자료는 없으나…"
비영리민간단체 여부  → "비해당"   근거: "…관련된 자료가 없음"
```

근거란에 "자료가 없다"고 쓰면서 값을 채웠다. 부탁으로는 막을 수 없다.
그래서 LLM의 협조가 필요 없는 결정론적 검사 두 개를 출력 뒤에 둔다.

**가드 ① 근거 대조 (`quotesSource`)**
모델이 제시한 인용이 자료(B)에 실제로 존재하는 문자열인지 대조한다. 없으면 값을 버리고
비워둔다. 공백·문장부호 차이는 정규화해서 허용한다. 값 자체가 자료에 그대로 있으면
그것도 근거로 인정하되, **4자 미만은 인정하지 않는다** — 값 `"해당"`이 자료의
`"해당사항 없습니다"`에 우연히 포함돼 환각이 통과한 사례가 있었다.

**가드 ② 되묻기 정리 (`refineQuestions`)**
모델은 "확인차" 질문을 남발한다(서식1에서 **27건**). 후보 개수로 기계적으로 가른다.

| 후보 수 | 처리 |
|---|---|
| 2개 이상 | 진짜 모호함. 질문으로 남기고 **그 칸은 비운다** — 우리가 고르지 않는다 |
| 1개 | 확인 요청일 뿐. 질문을 버리고 그 값으로 채운다 (가드 ①은 그대로 적용) |
| 0개 | 자료에 없다는 뜻. 질문을 버리고 비워둔다 |

적용 후 서식1 기준 **질문 27건 → 1건**, 채움 42 → 54. 남은 1건은 자료에 연락처가
실제로 두 개 있는 항목이었다.

**두 가드는 확률적 실행이 아니라 고정 입력으로 검증한다** (`scripts/guard-test.ts`,
22개 케이스). LLM 실행은 매번 다르므로 "이번엔 안 지어냈다"는 "막았다"의 증거가 되지
못한다. 차단 케이스는 전부 solar-pro2가 실제로 만들어낸 출력을 그대로 넣었다.

## 11. `linesegarray` — 해결됨 (2026-09-10)

각 문단에는 `<hp:linesegarray>`라는 줄 렌더링 캐시가 있다.

```xml
<hp:lineseg textpos="0" vertsize="1100" baseline="935"
            spacing="660" horzpos="0" horzsize="10156"/>
                                      ↑ 이 줄의 폭
```

**증상**: 텍스트만 갈아끼우면 이 캐시는 옛 값으로 남는다. 한글은 `horzsize`(줄 폭)를
신뢰해 그 안에 글자를 배치하려 하고, 글자 수가 늘었으므로 자간을 밀어붙여
**글자끼리 겹쳐 그린다.** 표 구조는 건드리지 않았으므로 표는 멀쩡하고 글자만 겹친다 —
이 조합이 이 문제의 지문이다.

**발견 경위**: D1 스파이크는 값이 짧아(`제2015-041호` 등) 캐시 폭 안에 들어가 증상이
안 나타났다. Solar가 긴 값을 채우자 드러났다. **짧은 값만으로 검증하면 놓친다.**

**해결**: 값을 넣은 문단의 `linesegarray`만 제거하여 한글이 열 때 다시 계산하게 한다
(§11 초안의 세 경로 중 두 번째). 건드리지 않은 문단의 캐시는 그대로 두므로 무손상
원칙을 해치지 않는다. `linesegarray`는 `hp:run` 뒤의 형제 노드라 값 앵커와 구간이
겹치지 않고, 한 문단에 슬롯이 여럿이면 접어서 한 번만 제거한다.

글자 수가 변하지 않는 슬롯(체크박스 `【 V 】`, 인라인 공백 덮어쓰기)은 줄 폭이
유지되므로 캐시를 건드리지 않는다.

`FillOptions.dropLineSegs`로 끌 수 있으나 비교 검증용이며 기본값은 제거다.
A/B 검증: `scripts/lineseg-ab.ts` — 같은 값으로 캐시 유지본/제거본을 뽑는다.

### 남은 확인 사항

- 서식2(1,941슬롯)의 Solar 매핑 — 시간·비용 미측정
- 라벨 귀속 오류: 인라인 슬롯 `(우 )`에 엉뚱한 값이 배정되는 사례
- `capacity` 과소평가로 인한 넘침 (병합 셀에서 두드러짐)
