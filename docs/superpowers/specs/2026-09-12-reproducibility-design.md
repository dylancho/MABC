## 1. 배경

선행 설계는 **무손상**을 증명한다. "결과 파일이 원본 대비 서식을 깨지 않았다"를 바이트 단위로 보인다.

증명하지 않는 것이 하나 있다. **같은 입력을 두 번 넣으면 같은 파일이 나온다**는 보장이다. 무손상은 한 번의 실행에 대한 속성이고, 재현성은 실행들 사이의 속성이다. 둘은 별개다.

공문서 도구에서 재현성은 품질 항목이 아니라 신뢰의 전제다. 주무관이 같은 자료로 두 번 돌려 다른 문서를 받으면, 어느 쪽을 결재에 올려야 하는지 알 수 없다. 감사 상황에서 "이 문서가 이 자료에서 나왔다"를 재현해 보일 수도 없다.

### 1.1 실측 — 실제로 갈렸다

`D1-test/`에 같은 단계를 두 번 돌린 산출물이 남아 있었다. 열어서 비교했다.

| | 04-solar-531638 | 04-solar-936091 |
|---|---|---|
| 파일 크기 | 39,951 바이트 | 40,046 바이트 |
| 본문 텍스트 조각 수 | 119 | 118 |

크기만 다른 것이 아니라 내용이 갈렸다.

| 항목 | 실행 A | 실행 B |
|---|---|---|
| 금액 표기 | `1,850백만원` | `1,850` |
| 가입자 수 칸 | 비움 | `6`, `2`, `0` |
| 해당/비해당 체크 | `【 V 】` | `【   】` |
| 법인 주소 | 없음 | `서울특별시 성동구 왕십리로 222, 3층` |
| 정관 변경 이력 | 없음 | `2023.05.08`, `목적사업 조항 추가` |
| 담당자 표기 | `박서연 과장` 한 칸 | `박서연` / `과장` 두 칸 |

멘토 지적은 추상적 우려가 아니다. 이미 벌어진 일이다.

### 1.2 재현성의 두 층

용어를 나눈다. 이후 문서 전체가 이 구분을 쓴다.

- **내용 재현성**: 두 실행이 의미상 같은 문서를 낸다. 같은 칸에 같은 값이 들어간다.
- **바이트 재현성**: 두 실행의 파일 해시가 같다. 내용 재현성을 포함하며, 기계로 검증할 수 있고 무대에서 보여줄 수 있다.

목표는 바이트 재현성이다. 이유는 증명 가능성이다. 내용 재현성은 사람이 눈으로 비교해야 하고, 심사 시간 3분 안에 보여줄 방법이 없다. 해시 두 줄은 화면에 띄우면 끝난다.

## 2. 목표와 비목표

### 목표

- 같은 양식, 같은 자료, 같은 설정으로 두 번 실행하면 결과 hwpx의 SHA-256이 일치한다.
- 이 일치를 API 호출 없이 CI에서 검증한다.
- 배포된 웹앱에서 재현성을 시연할 수 있다. 현장 발표가 배포본으로 진행된다.
- 재현되지 않는 실행은 조용히 다른 결과를 내지 않고, 재현 불가임을 드러낸다.

### 비목표

- **모델 자체를 결정적으로 만들지 않는다.** 대규모 언어모델은 temperature가 0이어도 완전한 결정성을 보장하지 않는다. 서버측 배치 구성, 부동소수점 누적 순서, 모델 갱신이 변수다. 우리가 통제할 수 있는 것은 통제하고, 통제할 수 없는 것은 기록해서 우회한다.
- **모든 입력에 대한 사전 기록을 하지 않는다.** 처음 보는 양식은 실제 호출로 처리한다. 재현성 보장은 기록된 입력에 대해 성립하고, 기록되지 않은 입력은 그 사실이 드러난다.
- 캐시를 성능 최적화로 쓰지 않는다. 목적은 재현성이며 속도 개선은 부수 효과다.

## 3. 실측 — 비결정성의 출처

파이프라인 전체를 훑었다. 순수하지 않은 지점은 **네 곳**이며, 그중 문서 내용을 바꾸는 것은 두 곳이다.

### 3.1 샘플링 파라미터가 비어 있다 — 주원인

`src/lib/ai/map.ts:223`의 모델 호출에 `temperature`도 `seed`도 없다. 공급자 기본 샘플링이 그대로 적용되어 매 실행이 다른 토큰을 뽑는다. §1.1의 표기 흔들림과 값 유무 차이가 대부분 여기서 나온다.

SDK 타입 정의에서 두 설정이 모두 정식 지원됨을 확인했다 (`node_modules/ai/dist/index.d.ts` 394행, 437행).

### 3.2 청크 타임아웃이 벽시계에 매여 있다

`src/lib/ai/map.ts`의 `chunkTimeoutMs` 기본값은 90초이며 `AbortSignal.timeout`으로 걸린다. 제한을 넘긴 요청은 버려지고 그 칸들이 빈 채로 파일이 나간다. `maxRetries`가 0이므로 재시도 보정도 없다.

이것은 **네트워크 응답 속도가 문서 내용으로 새는 통로**다. 응답이 빠른 날과 느린 날의 출력이 다르다. §1.1에서 실행 A에만 주소와 정관 변경 이력이 통째로 없는 것이 이 패턴과 부합한다.

### 3.3 모델 이름이 별칭이다

`src/lib/ai/solar.ts:14`의 기본값 `solar-pro2`는 버전 별칭이다. 공급자가 뒤에서 가중치를 갱신하면 같은 코드가 다른 모델을 부른다. 우리 저장소에는 아무 변경도 없이 출력이 바뀐다. 이것이 가장 추적하기 어려운 종류의 비결정성이다.

### 3.4 ZIP에 현재 시각이 박힌다

`src/lib/hwpx/container.ts`의 재포장은 fflate `zipSync`를 쓰고, 압축 시각을 넘기지 않으면 라이브러리가 실행 시점을 기록한다 (`node_modules/fflate/lib/index.cjs:1889`). 내용이 완전히 동일해도 파일 해시가 매번 달라진다.

이 한 줄이 바이트 재현성의 문을 닫고 있다. 해시로 증명하는 길 자체가 막혀 있었다.

### 3.5 순수함이 확인된 것들

설계의 전제이므로 명시한다. 아래는 모두 같은 입력에 같은 출력을 낸다.

- `readContainer` — ZIP 중앙 디렉터리 직접 파싱, 순수
- `dissect` — 노드 인덱스에서 슬롯 IR 산출, 순수
- `extract` — 자료 텍스트 추출, 시각·난수·디렉터리 순회 없음
- `computeSubtotals` — 소계 계산, 순수
- `fill` / `inject` / `verify` — 정렬 비교자가 전순서이고 JS 정렬이 안정적이므로 순수
- `chunk` — 슬롯 입력 순서만으로 결정된다
- 배치 실행 — `Promise.allSettled`가 입력 순서를 보존하므로, 중복 제거의 "먼저 온 것을 쓴다" 규칙이 결정적이다
- `dedupeColumn` — 동점 시 먼저 온 것을 유지하며, 입력 순서가 결정적이므로 결과도 결정적이다

**결론**: 같은 양식이면 같은 프롬프트가 같은 순서로 만들어진다. 해시를 키로 응답을 재생하는 설계의 전제가 이미 갖춰져 있다.

## 4. 아키텍처

### 4.1 순수와 불순의 경계

```
┌─ 순수 계층 ─────────────────────────── 같은 입력 → 같은 출력 (검증됨) ─┐
│  readContainer · dissect · extract · computeSubtotals · fill · verify  │
└───────────────────────────────────────────────────────────────────────┘
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
        ┌───────────▼──────────┐    ┌───────────▼───────────┐
        │  불순 1: 모델 호출    │    │  불순 2: ZIP 압축 시각 │
        │  → 기록·재생으로 봉인 │    │  → 고정 상수로 봉인    │
        └──────────────────────┘    └───────────────────────┘
```

선행 문서 §4.4의 `hwpx-core`는 이미 "AI 의존성 0 · 네트워크 의존성 0 · 순수 함수"로 설계돼 있었다. 이 설계는 그 경계를 지키면서, 경계 밖 두 지점만 봉인한다. 새 계층을 넓게 만들지 않는다.

### 4.2 새 모듈 하나

`src/lib/ai/snapshot.ts`를 만든다. 책임은 셋뿐이다.

1. 호출 인자에서 캐시 키를 계산한다.
2. 스냅샷 맵에서 키를 조회한다.
3. 모드에 따라 재생하거나 실제 호출하거나 실패한다.

`map.ts`는 모델을 직접 부르지 않고 이 모듈을 거친다. 호출 지점이 `map.ts:223` 한 곳뿐이므로 갈아끼우기가 깔끔하다. 이 모듈은 ZIP도 XML도 슬롯도 모른다. 프롬프트와 응답만 안다.

### 4.3 캐시 키

키는 아래를 정규화한 JSON의 SHA-256이다.

- 모델명 — 별칭이 아닌 해석된 실제 버전
- 시스템 프롬프트 전문
- 사용자 프롬프트 전문 — 슬롯 목록과 자료 본문이 이미 여기 들어 있다
- 응답 스키마 — zod 스키마를 JSON Schema로 변환한 결과를 넣는다. SDK가 모델에 보낼 때 이미 만드는 형태이므로 새로 만들 것이 없고, 스키마를 고치면 키가 자동으로 바뀌어 낡은 스냅샷이 재생되지 않는다.
- `temperature`, `seed`

정규화는 키 순서를 사전순으로 고정하고 유니코드를 NFC로 정규화한다. 같은 양식과 같은 자료면 프롬프트가 동일하므로 키가 동일하다. §3.5에서 청크 분할이 순수 함수임을 확인했으므로 청크 경계도 흔들리지 않는다.

자료 본문이 키에 들어간다는 점이 중요하다. 자료가 한 글자라도 다르면 다른 키가 되어 재생되지 않는다. "같은 내용 인풋"의 판정을 사람의 판단이 아니라 해시에 맡긴다.

### 4.4 스냅샷 저장 — 생성된 모듈

`src/lib/ai/snapshots.generated.ts`가 키에서 응답 객체로 가는 맵 하나를 내보낸다. 기록 스크립트가 생성하고 저장소에 커밋한다.

이 형태를 고른 이유는 배포 환경이다. Vercel 서버리스는 실행 중 파일시스템이 휘발성이며 저장소에 쓸 수 없다. 생성된 모듈은 빌드 시점에 번들에 들어가므로 런타임 파일 읽기가 없고, 빌드 추적 설정에 의존하지 않는다. 현장 발표가 배포본으로 진행되므로 이 확실성이 값을 한다.

검토한 대안과 탈락 이유:

| 방식 | 탈락 이유 |
|---|---|
| JSON 픽스처 + `outputFileTracingIncludes` | 증명 장치가 설정 한 줄에 매달린다. 조용히 깨지고 배포 환경에서만 재현된다. |
| Vercel Blob 또는 KV 조회 | 네트워크와 외부 상태가 다시 끼어든다. 재현성을 주장하는 코드가 재현 불가능한 것에 의존한다. |

번들 크기는 공모전 규모에서 문제가 되지 않는다. 양식 종류가 목표 8종이고 양식 하나의 스냅샷이 수십 KB 수준이다.

### 4.5 모드

환경변수 `REPRO_MODE` 하나로 정한다.

| 값 | 동작 | 용도 |
|---|---|---|
| `strict` | 스냅샷이 없으면 실패한다. 실제 호출을 하지 않는다. | 현장 시연, 골든 테스트, CI |
| `prefer` | 있으면 재생, 없으면 실제 호출 | 평소 운영 기본값 |
| `off` | 항상 실제 호출 | 새 양식 탐색, 프롬프트 수정 중 |

기본값은 `prefer`다. 스냅샷이 없는 새 양식도 평소처럼 동작하게 하려는 것이다. 재현성 보장은 기록된 입력에 대해 성립하고, 그 경계가 응답 메타에 드러난다.

### 4.6 기록 명령

`scripts/record.ts`는 로컬 전용이다. 양식과 자료를 받아 `off` 모드로 실제 호출을 하고, 얻은 응답으로 스냅샷 모듈을 다시 써낸다. 배포본에는 기록 경로가 존재하지 않는다.

기록은 사람이 명시적으로 돌리는 행위다. 실행 중에 저절로 캐시가 채워지면, 무엇이 언제 기록됐는지 추적할 수 없고 저장소 상태와 배포 상태가 갈라진다.

## 5. ZIP 압축 시각 고정 — 함정 둘

단순해 보이는 항목인데 순진한 구현이 두 번 틀린다. 둘 다 코드로 확인했다.

### 5.1 `mtime: 0`은 예외를 던진다

fflate 문서는 "수정 시각을 완전히 감추려면 0으로 설정"을 권한다. 이 조언을 ZIP에 그대로 쓰면 앱이 깨진다.

`node_modules/fflate/lib/index.cjs:1889` 부근이 연도를 1980 기준으로 인코딩하고, 범위를 벗어나면 예외를 던진다.

```js
var dt = new Date(f.mtime == null ? Date.now() : f.mtime), y = dt.getFullYear() - 1980;
if (y < 0 || y > 119)
    err(10);
```

`mtime: 0`은 1970년이 되어 `y`가 음수가 되고 에러 10이 난다. 값은 1980년부터 2099년 사이여야 한다.

### 5.2 고정 epoch 숫자도 시간대에 따라 달라진다

위 코드가 `getFullYear`, `getMonth`, `getDate`, `getHours`를 쓴다. 모두 **지역시각** 접근자다. 고정된 epoch 밀리초를 넘기면, 한국 시간대인 개발 노트북과 UTC인 Vercel이 서로 다른 DOS 시각 바이트를 만든다. 로컬에서 맞던 해시가 배포본에서 틀어진다.

해법은 **지역시각 생성자로 만든 상수**다.

```ts
const FIXED_MTIME = new Date(1980, 0, 1, 0, 0, 0);
```

이 생성자는 지역시각으로 1980년 1월 1일 0시를 만들고, fflate는 지역시각 접근자로 그것을 읽는다. 생성과 읽기가 같은 시간대를 쓰므로 상쇄된다. 어느 시간대의 어느 기계에서도 동일한 바이트가 나온다.

모든 엔트리에 이 값을 넘긴다. `mimetype`의 STORE 규약은 선행 문서 §4.3대로 유지된다. 압축 시각은 ZIP 헤더의 별도 필드이므로 압축 방식과 무관하다.

### 5.3 항등 테스트와의 관계

선행 문서 §9의 항등 테스트는 "값 없이 `fill()` 실행 → 원본과 바이트 단위로 동일"을 요구한다. 압축 시각을 고정하면 이 테스트가 **오히려 더 엄격해진다**. 지금까지는 시각 필드가 원본과 다를 수밖에 없었으므로 항등 검사가 그 필드를 우회했거나 원본 시각을 보존했을 것이다. 구현 시 이 상호작용을 먼저 확인한다. 원본 시각을 보존하는 경로가 이미 있다면 고정 상수와 충돌하지 않는지 결정해야 한다.

**열린 문제로 남긴다.** 두 선택지가 있다. 원본 엔트리의 시각을 그대로 보존하면 항등성이 강해지고 재현성도 얻는다. 입력 양식 파일이 고정이므로 시각도 고정이기 때문이다. 고정 상수를 쓰면 입력 파일의 시각이 달라도 출력이 같아진다. 전자가 무손상 주장에 더 부합하므로 전자를 우선 시도한다.

## 6. 부분 실패 정책

현재 동작은 청크 실패 시 그 칸들을 비우고 파일을 내보낸다. 코드 주석이 밝히듯 이것은 의도된 선택이었다. "Solar가 한 번 늦어도 파일은 나온다."

재현성 관점에서 이 선택은 성립하지 않는다. 무엇이 비었는지가 네트워크 상태에 달려 있으면 출력이 재현되지 않는다.

정책을 모드에 연동한다.

- `strict`: 청크 실패 시 파일을 만들지 않고 사유를 반환한다. 스냅샷 재생에는 네트워크가 없으므로 이 경로는 사실상 발생하지 않는다.
- `prefer`, `off`: 현재 동작을 유지하되, 실패로 비운 칸 목록을 응답 메타에 명시한다. 지금은 개수만 요약에 실린다.

반쪽 문서를 내주는 것 자체는 유지한다. 마감 직전 현장에서 아무것도 못 받는 것보다 낫다는 기존 판단은 옳다. 바꾸는 것은 **그것이 재현 가능하다고 주장하지 않는다**는 점이다.

## 7. 증명 하네스

재현성은 주장이 아니라 실행 결과로 보여야 한다. 두 개를 만든다.

### 7.1 `scripts/repro-check.ts` — 두 번 돌려 비교

`strict` 모드로 전체 파이프라인을 두 번 실행하고 두 결과의 SHA-256을 비교한다. 불일치 시 어느 칸이 갈렸는지 출력한다.

비교 방식은 §1.1에서 쓴 것을 그대로 재사용한다. 두 hwpx의 본문 XML에서 텍스트 노드를 뽑아 한쪽에만 있는 값을 나열한다. 이 방식이 실제로 문제를 드러냈으므로 검증된 진단 도구다.

### 7.2 골든 파일 테스트

저장소에 입력 양식, 입력 자료, 기대 출력 해시를 둔다. `strict` 모드로 돌아가므로 API 호출도 네트워크도 필요 없다. `npm test`로 실행된다. 현재 `package.json`에 테스트 명령이 없으므로 함께 추가한다.

선행 문서 §9의 골든 테스트가 "파싱 성공 / 슬롯 수 스냅샷 / verify 통과 / diff 범위"를 본다. 여기에 **출력 해시 일치**를 한 줄 더한다. 별도 테스트 체계를 세우지 않고 기존 항목에 붙인다.

이 테스트 결과가 심사 자료에 붙일 증거다. "재현됩니다"라는 문장보다 통과한 테스트 출력이 강하다.

### 7.3 현장 발표에 넣을 장면

선행 문서 §10의 3분 시나리오는 무손상 리포트에서 끝난다. 재현성 장면을 한 박자 더한다.

```
2:15  같은 입력으로 한 번 더 돌린다
      두 파일의 해시를 나란히 띄운다 — 동일
      "어제 돌린 것과 오늘 돌린 것이 같은 문서입니다.
       감사에서 재현해 보일 수 있습니다."
```

15초짜리 장면이고, 무손상 다음에 놓이면 논지가 이어진다. 깨지지 않는다, 지어내지 않는다, 그리고 흔들리지 않는다.

## 10. 열린 문제

1. **원본 시각 보존과 고정 상수 중 무엇을 쓸지.** §5.3. 항등 테스트 현재 구현을 읽고 결정한다. 구현 첫 항목이다.
2. **Upstage가 `seed`를 존중하는지.** 모른다. 실측으로 확인하되, 재현성 주장을 여기에 걸지 않는다. 존중한다면 스냅샷 없는 입력의 안정성도 함께 오른다.
3. **`temperature: 0`이 인용 검증 가드와 어떻게 상호작용하는지.** 선행 문서 §8.1의 두 가드가 모델 출력을 기계적으로 막는다. 온도를 내리면 통과율이 오를지 떨어질지 예측할 수 없다. 기록 전에 한 번 재보고, 채움률이 떨어지면 발표 자료의 수치를 갱신한다.
4. **스냅샷을 어느 양식까지 기록할지.** 최소한 발표에 쓰는 양식과 자료 한 쌍은 반드시 기록한다. 목표 8종 전체는 시간이 남으면 한다.
